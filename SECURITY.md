# Security Policy

OpenForms handles form responses that are frequently personal data. We take
vulnerability reports seriously and will work with you in good faith.

## Supported versions

While the project is pre-1.0, only the **latest released version** receives
security fixes. Self-hosters should track the newest tag.

| Version | Supported |
|---|---|
| 0.1.x | ✅ |
| < 0.1 | ❌ |

## Reporting a vulnerability

**Please do not open a public issue for a security problem.**

Report privately through either channel:

1. **GitHub Security Advisories** — [Report a vulnerability](https://github.com/Klaynight-dev/Openforms/security/advisories/new) (preferred).
2. **Email** — <elouanpassereau@gmail.com>.

Please include, as far as you can:

- The affected version or commit.
- A description of the vulnerability and its impact.
- Reproduction steps or a proof of concept.
- Any suggested mitigation.

### What to expect

| Stage | Target |
|---|---|
| Acknowledgement of your report | 72 hours |
| Initial assessment and severity rating | 7 days |
| Fix released for a critical issue | 30 days |
| Public advisory | After the fix ships, coordinated with you |

We will credit you in the advisory unless you prefer to stay anonymous.
This is a volunteer project with no bug bounty programme.

## Scope

**In scope** — the code in this repository: the API, the web UI, the embed
widget, the Docker images and the default configuration they ship with.

**Out of scope**

- Vulnerabilities in a self-hoster's own deployment (misconfigured reverse
  proxy, exposed database, weak secrets, outdated host OS).
- Findings that require an already-compromised administrator account.
- Missing hardening headers with no demonstrated impact.
- Denial of service through raw traffic volume.
- Reports generated by an automated scanner with no verified exploitability.

## Deployment security notes

Some risks are the operator's responsibility. If you self-host, please:

- **Back up `ENCRYPTION_KEY` separately from the database.** Losing it makes
  every encrypted response permanently unreadable; leaking it alongside a
  database dump makes encryption at rest worthless.
- Generate unique `ENCRYPTION_KEY` and `SESSION_SECRET` values. Never ship the
  placeholder values from `.env.example` or the compose defaults to production.
- Serve the app over HTTPS with `COOKIE_SECURE=true`.
- Restrict `FRONTEND_ORIGIN` to the origins you actually serve.
- Treat API keys as passwords — they are shown once at creation and stored
  hashed. Rotate them when a holder leaves.
- Keep the instance updated; subscribe to repository releases.
